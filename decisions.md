# Decisions Log — quick version

## The basics
- Rules live in the database, not buried in code — so someone can change a threshold without needing a new deploy. If a team lead wants "20 tickets" to become "15," that's a form, not an engineering ticket.
- Split into three simple pieces: one takes in the data, one checks it against the rules, one sends the alert. Each piece stays simple and can be tested on its own without dragging the other two along.
- Used tools I already know well (FastAPI, Postgres) so my time went into the hard problems, not learning a new framework. Kept the frontend tiny on purpose — just a list of rules and a form to edit them, no login system, no fancy drag-and-drop builder.
- Keep the rules sitting in memory instead of hitting the database on every single event — too slow once you're talking millions of events a day. Refresh that memory every few seconds instead of chasing instant updates (more on why below — that's one of the two things I want to explain properly).
- Some things can't be caught just by reacting to events — like "this agent has been on one call for 45 minutes." Nothing tells you that while the call's still going, the system only hears about it once the call ends. So on top of reacting to events, it also checks in on its own every so often, just to catch things that are true because time passed, not because something happened.
- Don't repeat the same alert over and over while a problem is still ongoing — only alert once, right when it starts. Otherwise a queue that's backed up for twenty minutes pings someone forty times instead of once.
- Originally built for team leads *and* agents — team lead as the main command-center experience, agents getting a lighter self-service layer for their own adherence (`adherence_self`, since removed — see "Single-team scope" below for why). Skipped head-of-support on purpose — that's a different feature entirely (a rolled-up summary, not a real-time alert), left out and named as a cut, not built half-way. Rule table itself doesn't hardcode "team lead" anywhere at the data layer — the recipient is just a person, so it *could* stay flexible — but the API contract now assumes a single recipient by default; see "Single-team scope" below for why that flexibility got dropped from the surface a user actually sees.
- The sample data had real messiness — one event repeated itself, and one showed up about an hour late. That's normal in real systems, not a bug in the data. Built two small checks for it: skip anything already seen, and never let old information overwrite something newer that already arrived.
- Also noticed "no queue" gets written two different ways in the data — sometimes `null`, sometimes an empty list — same meaning, different shape. Fixed by cleaning it up to one shape as soon as it comes in, so nothing later in the system has to check for both.

## Why "check every few seconds" beats "instant updates"
Instant updates need a connection that stays open the whole time, listening for changes. The problem is that kind of connection can quietly die — a network blip, a restart, whatever — and nothing tells you it broke. You'd have to build extra code just to notice that and reconnect. All that extra work buys you one thing: a rule change takes effect instantly instead of a few seconds later. Nobody's sitting there needing it that fast — an ops manager editing a threshold doesn't care if it's live in one second or three. Checking every few seconds gets the same result, is simpler to build, has way less that can break, and nobody would ever notice the difference.

## The "late, but maybe still true" question
One event in the sample showed up about an hour late — not broken, just delayed, the way messages sometimes are in real systems. My rule for handling that: never let old information overwrite something newer you already have. That part's solid and it's in the code. But it raised a fair question — what if nothing newer has come in yet? Is that late information actually still useful, or just noise? I didn't build the fancier version of that (checking whether the situation has already changed before deciding to alert on it) because it only shows up once in the sample data, and chasing it would've eaten time for very little payoff on a project this size. But it's a real limitation, not something I missed — worth saying out loud in the presentation as a "here's what I'd build next" instead of pretending it isn't there.

# Implementation Log

Everything below happened after the design above was approved and we started actually building. Kept separate from the design section since this is "what got built and what came up while building it," not "what we planned."

## What actually got built, in order

1. **Ingestor** (`app/ingestor/`) — Pydantic models per event type (`schemas.py`), idempotency (drops duplicate `event_id`s), null normalization. Tested without any database — pure logic.
2. **Engine** (`app/engine/`) — `Rule` base class (reactive: `entity_key()` + `is_violating()` + `render_message()`) and `DurationRule` base class (tick-based: `watched_state()` + `is_too_long()`, checked via `Engine.tick()` instead of from an event). Built and proved out with the two most different rule shapes first: `QueueBacklogRule` (reactive) and `LongCallRule` (duration-based) — deliberately picked one of each so the pattern was proven twice, not just once, before building more. Correction: the original design spec described `tick()` as running on an independent background timer (sleep-loop). What's actually built calls it synchronously, right after processing each incoming event, using that event's own timestamp as "now" (`app/api/routes/events.py`). That's a deliberate improvement, not a shortfall — it ties duration checks to the data's own timeline instead of wall-clock, which is exactly what makes the compressed-speed demo replay work correctly for `long_call`/`adherence_escalated` without needing a real-time timer running alongside a sped-up data feed.
3. **`RuleStateTracker`** — the no-repeat-alert mechanism. Only fires a notification on the ok→firing transition. Proven with tests that specifically check "stays firing → no repeat" and "recovers then breaches again → fires fresh."
4. **Persistence** (`app/persistence/`) — `rules` / `rule_state` / `notifications` tables, a `rule_type` → class registry (`app/engine/rules/__init__.py`), and a loader that turns a database row back into a live `Rule` object.
5. **Router** (`app/router/`) — persists a notification and hands it to a delivery function (defaults to printing to console, which is the stub delivery the prompt asks for).
6. **API** (`app/api/`) — FastAPI app. Full CRUD on rules (create/list/edit/delete), notifications (list/resolve/unresolve/delete), and a `POST /events` endpoint that feeds the live running engine. The app bootstraps its own database schema on startup (`Base.metadata.create_all`) so it works against a genuinely empty database with no separate migration step — appropriate for this scope, would be Alembic in a real production setup.
7. **The rule cache, for real this time** — `Engine.rules` is the in-memory cache we designed early on; a background poller (`app/api/rule_poller.py`) reloads it from Postgres every 5 seconds, so a rule created through the API takes effect without restarting the server. This was designed in the very first architecture conversation and only actually built once the API existed and made it necessary.
8. **Two demo scripts** — `scripts/demo_offline.py` (self-contained, builds its own engine, no server needed — good for a fast sanity check) and `scripts/demo_live.py` (a real HTTP client that replays `data/events.txt` against the actual running API and database, at a configurable pace via `--speed`, default 18x = ~5 real minutes). Kept both on purpose: one proves the core logic in isolation, the other proves the whole system integrated.
9. **Frontend** (`frontend/`) — Vite + React, no state library, no CSS framework, no router. Three panels: Active rules, Notifications, Resolved. A modal (triggered by a "+" button) handles both creating and editing a rule, reusing one `RuleForm` component in two modes. Colors and font pulled from Assembled's real marketing site (`#F8F7F3` background, `#222637` navy, `#00453D` teal, IBM Plex Sans) rather than invented — checked their actual site and product screenshots rather than guessing at "looks professional."

## Real bugs found by actually running the thing, not just writing tests

- **Missing `greenlet` dependency** — SQLAlchemy's async engine needs it; only surfaced when a test actually ran against a live database.
- **Event loop mismatch in tests** — the DB engine is created once at import time, but pytest was handing out a fresh event loop per test by default. Fixed with `asyncio_default_fixture_loop_scope`/`asyncio_default_test_loop_scope = "session"` in `pyproject.toml`.
- **No schema bootstrap for a fresh database** — tests always created their own tables via fixtures, but nothing did that for a real run of the app until `main.py`'s lifespan was taught to call `create_all` on startup. Found by actually starting the server, not by the test suite.
- **A live-crash in the frontend** — the create-rule form's live description preview called `.join(", ")` on `scope.agent_ids` before it had been converted from a raw typed string into an array, which only happened at submit time. Typing in that field threw mid-render and blanked the whole page. Fixed by normalizing once, before both the preview and the submit path use it, instead of normalizing only at submit time.
- **Whitespace/formatting fragility in rule matching** — a rule created with `"billing "` (trailing space) or agent IDs typed as `"a_11 a_12"` (no comma) would silently never match anything, since matching was an exact string comparison. Fixed at the matching layer (`.strip()` on both sides in `QueueBacklogRule`/`LongCallRule`, so it's correct regardless of where the data came from) and at input time (the agent-IDs field now splits on comma or whitespace).
- **Negative numbers accepted** — nothing stopped a threshold or a duration from being negative, which makes no product sense (can't have -5 tickets waiting). Fixed at the API layer, not just the UI, since the UI can be bypassed via curl/Swagger: `severity` is now bounded 1–10 via Pydantic's `Field(ge=1, le=10)`, and a generic check rejects any negative number in a rule's `params`.

## The one real incident: running tests wiped live dev data

**What happened:** tests and the live dev/demo session were pointed at the exact same Postgres database. The test fixtures do a full `create_all` → yield → `drop_all` cycle around every test. Running the test suite while the user had manually created real rules through the running app caused `drop_all` to destroy that data — rules they'd typed by hand were permanently gone.

**Root cause:** `DATABASE_URL` had one default, used everywhere — tests, the dev server, the demo scripts — with nothing separating "data I'm experimenting with" from "data a test fixture is allowed to nuke."

**Fix:** tests now get their own database (`notifications_test`, a separate Postgres database inside the same container). `tests/conftest.py` sets `DATABASE_URL` via `os.environ.setdefault(...)` before anything imports `app.persistence.database` (env var has to be set before that module's import-time `create_async_engine()` call runs). This makes the mistake structurally impossible going forward, not just "be careful next time."

**Lesson for next time a shared resource like this comes up:** before running a destructive-by-design test suite (anything that drops/truncates tables), verify it's pointed at a database nobody is actively using for real work — don't assume based on how the fixture is scoped.

## Design decisions made or refined during implementation (not just at the start)

- **Severity is per-rule-instance, not fixed per rule type.** Originally planned as a fixed property of each rule class. Changed after direct feedback: different team leads will disagree on what's most urgent to them, so it's a value on the rule row (with a `default_severity` per type only used to pre-fill the creation form), not baked into code.
- **Deleting a rule keeps its notification history.** First version cascaded the delete (removing a rule also deleted its past notifications). Reconsidered: a notification's message/severity/recipient are already stored on the notification row itself, so it stays meaningful even after the rule that caused it is gone. `notifications.rule_id` is nullable with `ON DELETE SET NULL`; only `rule_state` (unused, no history value) cascades.
- **Resolve/unresolve workflow for notifications**, added after the core system was working: `resolved` boolean on notifications, a third UI panel ("Resolved") separate from the live feed, undo available (mark unresolved again) since a resolve can be a misclick, and delete available from both panels, not gated behind resolving first.
- **`rule_state` (the table meant to make the no-repeat-tracker survive a restart) was deliberately left unbuilt**, with the reasoning documented directly on the class in `app/persistence/models.py` rather than in a comment buried in this file — so a cold reader of the code sees the limitation exactly where it matters, not just in project notes.
- **Percent-shaped fields (`pct_of_sla`, `pct_over_forecast`, `occupancy_threshold`) take a whole-number percentage (`80`), not a fraction (`0.8`).** First version asked for a fraction, which silently collided with a real HTML bug: `<input type="number">` defaults to `step="1"` when no step is set, so the browser's native validation rejects decimals on submit — the field could only actually accept whole numbers, which made "0.8" impossible to submit at all. Fixed by asking for the number people actually think in (a percentage) and converting to a fraction only at the point of sending it to the backend, rather than fighting the browser.

## `TeamAdherenceCapacityRule`'s extra state, and the poller-refresh bug it caused

Two things worth separating clearly, since they're easy to conflate:

**1. It's the one rule that has to remember things across events.** Every other rule can answer "is this violating?" from a single incoming event. This one can't — no single `adherence_check` event knows about more than one agent, so it has to keep its own running tally ("who's currently violating") as events trickle in, one agent at a time.

**2. That tally used to get silently wiped every ~5 seconds.** The rule cache poller rebuilds every `Rule` object from the database on each refresh. For every other rule that's harmless — they don't remember anything between events anyway. For this one, it meant the tally reset to empty on every refresh, even though nothing had actually changed for the agents already in violation. Concretely: if two agents were already violating and a third joined right as a refresh landed, the fresh rule object would only "see" the third agent — undercounting 3 as 1, and potentially never firing an alert for a real, currently-true situation, if the first two recovered before sending another event.

**Fix:** a `carry_over_state(previous)` hook on the `Rule` base class — a no-op for every rule except this one. `Engine.set_rules()` calls it on each new rule during a refresh, matching by `rule_id` against what was there before, so `TeamAdherenceCapacityRule` can copy its tally forward instead of starting blank. Proven by `tests/test_new_rule_types.py::test_team_adherence_capacity_tally_survives_a_rule_cache_refresh`, which constructs a fresh rule object (simulating exactly what the poller does) and confirms the tally is preserved rather than reset.

**A more general fix was considered and deliberately not built:** instead of a per-rule hook, the poller could diff old vs. new rule rows (by `id` + `updated_at`) and only rebuild rules that actually changed, leaving untouched rules — and any state they carry — completely alone. That would solve this for any future rule with similar memory, automatically, with no hook to remember. Not built because it adds real machinery (state that has to persist across refreshes outside the Engine, correct handling of a rule being disabled/deleted mid-diff, more surface area to test) to solve a problem exactly one rule type currently has. The hook is small, isolated, and easy to delete wholesale if a second rule ever needs similar memory — it's not debt that compounds, since nothing else depends on it existing. Worth naming explicitly in the interview: seeing the general solution and choosing the narrower one *on purpose*, because the cost didn't match the number of real cases, is the actual signal — not which one got built.

## Single-team scope: dropping "who to notify" and naming the whole roster

Looked again at `data/events.txt` and realized an assumption had been baked in without ever saying it out loud: every agent ID that appears (`a_05` through `a_88`, 8 total) is treated as this system's entire world. That's not an org-wide feed — it reads like one team's roster. Two UI decisions followed directly from actually naming that assumption:

**1. The "Notify (recipient id)" field on the rule form was removed.** It asked a rule author to type who should get the alert, every single time, even though — under the one-team assumption — the answer is always the same person, the team lead watching this dashboard. Asking a repeated question with only one real answer is friction, not flexibility. `recipient_id` still exists end-to-end in the code (`Rule`, `RuleRow`, `NotificationRow`, the router) because ripping it out would mean an actual database migration for no real benefit at this scope; the API layer just stopped accepting it from a client and the server fills in a constant (`DEFAULT_RECIPIENT_ID = "lead_maria"`, in `app/api/schemas.py`) when a rule is created. Nothing about the engine, persistence, or delivery layer changed — this was a UI/API-contract decision, not an architecture one. If this ever needed to support multiple teams or multiple recipients again, the field is one line to bring back in both the schema and the form; nothing was deleted at the layers that would make that hard.

**2. Agent IDs got a readable form, and lists of them stopped being enumerated once they get long.** `a_19` reads fine as a single value in a dropdown, but a sentence like "Notify me if any of a_19, a_88, a_31, a_11, a_23, a_42, a_05, a_07 are off-schedule" — the realistic shape once someone actually builds a team-wide rule — is exactly the kind of run-on list that stops being readable. Fixed at the display layer, in `frontend/src/knownEntities.js`:
- `formatAgentName("a_19")` → `"Agent 19"` — used everywhere an ID is shown to a person (dropdown options, checkbox labels, rule descriptions). The raw `a_19` string is still what's matched and stored; only the label changed.
- `formatAgentList(ids)` — natural joining for small selections ("Agent 19 and Agent 88", Oxford comma for three+), but once a selection covers the *entire* known roster, it collapses to `"your whole team"` instead of naming all 8. This only reads correctly because of the one-team assumption above — "your whole team" would be meaningless (or wrong) against a real org-wide agent directory. If agent lists ever needed to scale past one small team, this would need to become "N of your team" with a real count instead of an implicit "all of them = the team" check.
- The rule form's agent checkboxes got a "Whole team" master checkbox (checks/unchecks all `KNOWN_AGENTS` at once) so selecting everyone doesn't mean 8 individual clicks.

**3. `adherence_self` (the private self-nudge to an agent about their own schedule) was removed outright, not just deprioritized.** It was fully built and tested — reactive rule, its own test coverage, its own form fields — and got deleted anyway once the single-team-lead assumption was actually said out loud: the main (only, in this build) user is the team lead, so a feature whose entire point is "notify the agent themselves, privately" doesn't fit who's using this system. Kept as scope creep would've been the easy path — it already worked, deleting it costs nothing functionally and risks looking like wasted effort. Cut anyway, deliberately, rather than left in because it was cheap to leave in: `app/engine/rules/adherence_self.py` deleted, its `RULE_REGISTRY` entry and import removed (`app/engine/rules/__init__.py`), its two unit tests removed (`tests/test_new_rule_types.py`), and the frontend's `agent_id`-single-select scope-field code path deleted along with it since nothing else used that shape. No rows existed for it in the live database at the time, so no data cleanup was needed. If agent self-service ever comes back as a real requirement, `git log` has the original implementation to resurrect rather than rebuild from scratch.

## Card layout: title above the sentence, and making every sentence actually parse

Two rounds on this. First attempt tried to make the plain-language description (e.g. "Notify me when billing has more than 10 tickets waiting") more prominent by making it bigger (16px/medium-weight) and moving it above the type tag — wrong on both counts. Settled layout: type tag + severity badge lead the card (the tag stayed a quiet uppercase label — that part helped), the description follows underneath at normal size (14px) — title before content is the more readable order, not the reverse. Same fix applied to the rule-creation modal in a different way: the live preview sentence used to sit at the bottom of the form, below every field, requiring a scroll to see it update; moved to right under the rule-type dropdown so it's visible while filling out the rest of the form.

Separately, a few of the generated sentences didn't actually read as English — "Warn me when billing is close to missing its SLA (70%)" leaves "(70%)" dangling with no stated relationship to anything. Rewrote every percent-based description in `frontend/src/ruleTypes.js` to state what the percentage measures: `sla_risk` → "...longest wait reaches 70% of its SLA deadline", `volume_surge` → "...call volume runs more than X% above what was forecasted", `occupancy` → "Notify me when X% of {queue}'s agents are busy on calls" (dropped the word "occupancy" from the sentence entirely — it's jargon that has to be explained, the plain description shouldn't require already knowing the metric name to parse). Also caught and fixed a real bug while doing this: the percent fields used `value * 100 || "?"` to fall back to a literal `?` character when nothing had been typed yet — except a legitimately-empty field normalizes to `0`, and `0 || "?"` treats that `0` as falsy, so the live preview showed a stray "?%" any time the field was blank, not just when something was actually wrong. Fixed to just show the real number (`0%`) — consistent with how non-percent fields like `threshold` already behaved (they use `??`, which correctly leaves `0` alone).

One correction on scope: "SLA" staying in the *generated sentences* (not just the rule-type label) turned out to be fine after all — the confusing part was only the `?%` bug, not the acronym itself. So `sla_risk`/`sla_breach`'s sentences keep saying "SLA deadline" / "missed its SLA," on purpose, rather than being rewritten into a jargon-free paraphrase. The click-to-reveal hint is still where a first-time team lead learns what SLA means; the sentence itself doesn't need to re-teach it every time.

A second correction, this time on accuracy rather than wording: the `adherence_escalated` / `team_adherence_capacity` hints originally said an agent had been "away." Checked the actual code and sample data before shipping that word, and it's not quite right — this system doesn't decide what counts as an adherence violation itself; each `adherence_check` event arrives with `in_violation: true/false` already set by whatever upstream schedule-tracking system produced it (`app/ingestor/schemas.py::AdherenceCheck`), and the rule (`app/engine/rules/adherence_escalated.py`) only reacts to that flag once it's stayed true past the duration threshold. Looking at what the sample data actually flags: being on a call while scheduled available is *not* a violation (that's the job), but an unscheduled break or an unscheduled meeting while scheduled available *is*. "Away" implies not at work; a meeting is still work, just not on the phones. First fix ("doing something other than what their schedule says, like an unscheduled break or meeting") was accurate but too wordy, and listing the specific states (break, meeting) turned out to be unnecessary detail — a team lead doesn't need to know *what* an agent's doing instead, just that they're not where their schedule says. Settled on "off schedule," plain, no examples in parentheses.

Added a plain-language explanation for each rule type (`RULE_TYPES[type].hint`) so the metric names that stay jargon-y in the tag itself (like "Occupancy") aren't a dead end. Went through two wrong homes for it before landing on the right one:
1. Native `title` attribute on the rule-type tag — smallest possible implementation, but unreliable (needs the mouse to sit still for about a second, easy to miss).
2. A custom pure-CSS tooltip (`::after` pseudo-element on `:hover`) — fixed the reliability problem, but hover on a tag inside a scrolling rule list turned out to have two deeper problems: it's not discoverable (nothing signals it's hoverable) and it gets visually clipped by the panel's `overflow-y: auto` scroll container.
3. **Landed on**: a click-to-reveal "ⓘ what's this?" button next to "Rule type" in the create/edit modal (`RuleForm.jsx`), toggling a short paragraph (`.rule-type-hint`) below the dropdown. Click instead of hover works identically on touch, the button itself signals "there's more here," and it lives in the modal (where you're actively choosing a type) rather than on every already-created rule card, where the same explanation would just be repeated noise.

The first draft of the hint text itself missed the actual goal. It's meant for someone brand new to being a team lead who doesn't know the contact-center vocabulary yet, but the first pass just restated the rule name in slightly different words ("Fires when too many tickets are waiting in this queue" for a rule literally called "Queue backlog") — redundant with the label, taught nothing. Rewrote all 9 to actually explain the underlying idea instead: what "SLA" means in plain terms (a promised response time) without using the acronym, what "adherence" means (being where your schedule says you should be) without using that word, and why `occupancy` and `zero_coverage` are different severities of the same underlying problem. Also dropped the word "fires" (engineering jargon for "triggers," not something a new team lead would know either) in favor of "tells you when."

Also worth noting: a related "half baked" report turned out not to be a real bug — the live rule-creation preview showing "more than 0 of your whole team are off-schedule" before the count field was filled in looked broken, and a fix was built and then explicitly un-done after clarifying: seeing the sentence update in real time, blanks and all, is preferred over hiding it until the form is complete. Reverted rather than left half-applied.

## Current state (what's built vs. what's left)

**Built and working, verified live (not just by tests):** ingestor, engine (reactive rules, duration-based rules, and the one aggregate rule with its own cross-refresh memory), no-repeat-alert tracking, persistence, router, full rule CRUD via API, `/events` ingestion endpoint, the rule-cache poller, both demo scripts, and a complete frontend (create/edit/delete rules via modal, active/resolved notification panels with resolve/undo/delete, Assembled-derived visual design).

**Rule catalog: 9 rule types implemented** — `queue_backlog`, `sla_risk`, `sla_breach`, `volume_surge`, `zero_coverage`, `long_call`, `adherence_escalated`, `team_adherence_capacity`, `occupancy` — each following one of the patterns proven early on (reactive `Rule`, duration-based `DurationRule`, or the aggregate variant described above), all creatable through the frontend. (A 10th, `adherence_self`, was built and later removed once scope narrowed to team-lead-only — see "Single-team scope" above.)

**Explicitly not built, and why:**
- `rule_state` persistence (see above) — named limitation, not an oversight.
- The more general "diff the poller" fix (see above) — named tradeoff, not an oversight.
- Real Slack/email delivery — out of scope per the prompt; console + persisted notification log is the stub.
- Auth/multi-tenancy — out of scope per the prompt.

**Known rough edges, worth naming rather than hiding:**
- Frontend has automated tests now (Vitest + React Testing Library, `frontend/src/**/*.test.jsx`), but coverage is targeted at the riskiest logic (the two real bugs found — the agent-IDs crash and the percent-field conversion — plus the tier classification), not exhaustive component coverage the way the backend's pytest suite is for the engine.
- Params validation (`Field(ge=1, le=10)` for severity, a generic negative-number check for `params`) is a light guard, not exhaustive — e.g., nothing stops a `duration_min` of 0.5 or a wildly large threshold; good enough for this scope, not production-grade input validation.

## Occupancy's denominator, and where data trust actually has to live

Fair question that came up while reviewing notification wording: occupancy is `agents_on_call / (agents_on_call + agents_available)`, both numbers taken straight from the incoming `queue_snapshot` event. That denominator is "how many the snapshot says are logged in and live for this queue right now," not "how many people are actually assigned to this queue." An agent on an unlogged break, or one the snapshot system simply failed to report, is invisible to that math entirely.

**Built, tested, then deliberately reverted.** First response was to have `OccupancyRule` also watch `agent_state_change`/`adherence_check` events (which carry a `queue_ids` field, independent of what `queue_snapshot` reports) to build a running "known roster" for the queue, and flag when a snapshot's count came up short against it. This worked and was verified against two real discrepancies in the sample data (9:50, 10:16) — but the resulting message ("...but 1 more agent known to work billing isn't showing up in this count") turned out to be confusing rather than reassuring, even to the person who'd asked for it. Cost/benefit was wrong: real ongoing state (an unbounded, never-cleaned-up set per rule instance, blind for a while after every restart) for an ambiguous signal that fires on 2 of ~12 real snapshots. Reverted `OccupancyRule` back to the plain version rather than ship something that adds confusion without a clear payoff.

**The real question underneath it stands, and the honest answer is that this system can't answer it.** It has no independent way to verify `agents_on_call`/`agents_available` are correct — it fully trusts whatever the `queue_snapshot` event says. That's not a bug specific to this build; a downstream alerting system is only ever as trustworthy as its data source, and "how many agents are actually live on a queue right now" is properly the job of the system that's *routing the calls* (the real ACD/telephony platform — Genesys, Five9, Amazon Connect, etc.), not something an alerting layer should try to re-derive from a side channel. A real fix would mean integrating a second, independent, authoritative source (an actual workforce-management/scheduling system) and cross-checking headcount against it — genuinely new scope, not a tweak to one rule's message. Named here rather than solved, the same way `rule_state` persistence is.

## A claimed-done feature that wasn't actually done: the late-arriving-event guard

Both this doc's "basics" section and the original design spec describe the late-arriving-event fix as built: "never let old information overwrite something newer that already arrived." That was true of the *duplicate*-event check (idempotency, real, tested from the start) but not of the *out-of-order* check — nothing in the code actually compared an incoming event's timestamp against what was already stored before overwriting it. Found this by re-reading the claim skeptically instead of trusting that it was accurate, then proving it with a direct reproduction:

```python
tracker.update("a_19", "on_call", ts=9:30)
tracker.update("a_19", "available", ts=9:10)   # a late event, older timestamp
# before the fix: a_19 ends up recorded as "available" — the older event won
```

Two places had this exact gap, both fixed the same way (compare, discard if older, otherwise store):
- `AgentStateTracker.update()` — the shared per-agent state used by all duration-based rules (`long_call`).
- `TeamAdherenceCapacityRule` — keeps its *own* separate state (`_violating_agents`) rather than going through `AgentStateTracker`, so it needed its own separate timestamp guard (`_last_seen` per agent, carried across a rule-cache refresh the same way the violation tally already is). Proved this one was broken too before fixing it: a late, older "agent is fine now" event could silently erase a real, currently-true violation.

Both are covered by new tests (`tests/test_agent_state_tracker.py`, plus one added to `tests/test_new_rule_types.py`) that fail without the fix and pass with it. The lesson worth keeping, not just the fix: a claim being written down and sounding plausible isn't the same as it being true — this only got caught by re-deriving it from the actual code and proving it with a real reproduction, not by re-reading the documentation more carefully.
